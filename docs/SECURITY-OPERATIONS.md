# Security operations and technical evidence

This release adds security controls and verification tools. It does not certify the service as HIPAA compliant. A passing synthetic test or an empty alert list is not production approval. The MSP console deliberately reports technicalApproval=false while independent production/recovery review is outstanding.

## Logs and privacy

Workspace activity and security events are separate hash chains. Security events include successful authenticated API responses, authentication/authorization failures, request failures, sign-in/out, maintenance, storage checks and access reviews. Request IDs are generated by the server and returned as X-Request-ID. Routes are fixed categories; raw URLs, query strings, cookies, authorization headers, request bodies, file contents and supplied filenames are not collected by the security logger. Security actors are pseudonymous SHA-256 identifiers; the existing workspace activity log records staff identities. Account-target changes record a hash and role. Direct-download URLs now use opaque filenames rather than original names.

Migration 004 rejects UPDATE, DELETE and TRUNCATE on the activity, security-event and archive-reference tables. A schema owner can still remove database protections. Use a separate migration owner and a restricted runtime database role; the live database check reports owner privileges as attention. These protections are append-only controls, not a claim that a compromised schema owner cannot tamper with the database.

Hash verification runs in resumable 10,000-record windows and periodically restarts from the beginning. In-progress historical verification is not reported as complete. Archive batches independently validate their chain links and prior database checkpoint before uploading. Historical changes can be detected on a later scan; this is not instantaneous detection of every database-owner action.

## Approved 365-day archive

On November 20, 2026, the operator approved a separate private audit bucket with 365-day Object Lock. security-policy.json records that deployment policy. Maintenance creates only the deterministic sv-audit bucket for this portal, checks its ownership marker and encryption, and configures COMPLIANCE retention. It never enables retention on client file buckets. Retention cannot be shortened on already locked objects. Expiry permits deletion; this release does not automatically delete expired logs.

Automatic provisioning needs its existing bucket/key management capabilities plus readBucketRetentions, writeBucketRetentions, readFileRetentions and writeFileRetentions. Missing capabilities cause a recorded failure. An alternative is tools/provision-audit-archive.mjs, using an already-authorized B2 CLI, an explicit 365-day approval flag, and the production account fingerprint. It creates the dedicated bucket and restricted archive key without expanding the application's provisioning key. The maintenance-authenticated archive-connect operation verifies the production account, exact bucket/ownership marker, private encryption, retention and exact key capabilities before storing credentials encrypted. Do not expand client file credentials. The archive key has no deleteFiles, account management or bypassGovernance permission. The application encrypts each archive using AES-256-GCM under the stable credential-encryption key; storage also uses AES-256. Object names are random IDs.

Each batch is uploaded with an explicit COMPLIANCE retain-until date, read back, compared and decrypted, and its provider retention/version is checked before advancing the database checkpoint. Provider failures leave log records queued. A crash after provider acceptance but before the database commit can leave a locked, unindexed duplicate. Never delete an unfamiliar archive to repair a checkpoint. Recovery reconciliation must inspect its encrypted manifest. Latest-archive verification does not independently enumerate every possible orphan or prove the absence of a privileged database fork.

## Schedule, alerts and checks

vercel.json schedules GET /internal/security-maintenance every 15 minutes. CRON_SECRET is required; missing/incorrect authorization is rejected. The value is server-only and must be added to Production before deployment. Manual maintenance is MSP-only and requires normal authenticated/MFA/CSRF controls. Manual success does not stand in for scheduled-run evidence.

Maintenance checks log integrity, database TLS and ownership, offline uploaders, lack of successful uploader runs and stalled uploads, then archives bounded batches and verifies the latest archive. Database TLS evidence comes from the application's certificate-verified connection to the database endpoint, not pg_stat_ssl behind a provider proxy. It attempts one active workspace's synthetic storage check when that workspace has no check in the last day, or when a configured archive permits a missing cross-bucket negative test. A failed storage check is recorded without preventing log archival. The storage check verifies current private/encrypted/restricted-key configuration, a 17 MiB signed multipart upload and signed download, object AES-256, whole-file checksum, a range read, browser-origin preflight, and cross-bucket credential denial using another dedicated workspace or the scoped archive credential. An archive-to-client negative test is not a separate test between two clinical workspaces. Only the generated security-canary UUID is cleaned up. Failed cleanup requires operator review.

Alerts are durable dashboard records and can be acknowledged by an MSP. Acknowledgment is audited and does not repair the problem. New occurrences reopen alerts. Stale scheduled maintenance is visible in the dashboard after two hours. External alert delivery and independent monitoring are implemented in the managed-recovery release below, but require configured accounts and verified receipt before unattended production operation. An uploader heartbeat/success report is not a restore test or proof that every source file was protected.

## Least-privilege runtime role

Use an owner/migration connection in a protected local environment, not the deployed runtime:

    node --env-file=.env.owner tools/create-runtime-role.mjs --confirm-create-role --output .env.runtime-new

The tool creates a new non-owner role and writes its connection string to a protected, non-overwritten file. It grants normal application data writes, but only SELECT/INSERT on log tables, and no schema ownership. Set Vercel Production DATABASE_URL from that protected file, remove owner credentials from the runtime, redeploy and rerun maintenance. Keep the owner credential separately for npm run db:migrate using DATABASE_MIGRATION_URL before future schema upgrades. Verify rotation of any credentials previously shared in chat. This tool does not automatically change the production environment or assert that rotation occurred.

## Encrypted metadata backup and isolated recovery

Offline tooling supports metadata bundles up to 64 MiB of plaintext. Generate an independent 32-byte base64 RECOVERY_BACKUP_KEY, keep it in a protected offline secret store, and do not store it with the resulting bundle. This recovery key must differ from STORAGE_CREDENTIAL_ENCRYPTION_KEY. Protect the operator computer with disk encryption and restricted accounts.

    node --env-file=.env.recovery tools/security-backup.mjs backup --file <new-file.svbackup>

The tool reads a consistent repeatable-read database snapshot, verifies decryption of stored bucket credentials, and encrypts metadata plus the original credential-encryption key using AES-256-GCM. It does not copy file bytes or log connection strings. Store the encrypted bundle off the application host and keep its recovery key separately. No automatic Neon PITR or external backup destination is provisioned by this command.

For a drill, create a separate isolated project/database, set RESTORE_DATABASE_URL and RECOVERY_BACKUP_KEY in the protected local environment, and run:

    node --env-file=.env.recovery tools/security-backup.mjs restore --file <file.svbackup> --confirm-isolated-target --key-output <new-recovered-key.env>

The source and target connection endpoints/database names must differ when a source is supplied. The target must be empty. The encrypted bundle is authenticated before restore. The tool preserves file/bucket bindings and log order, excludes human sessions/enrollment codes, and revokes all restored device credentials. It writes the recovered credential-encryption key only to the protected output file. A recovery-review marker blocks new upload initialization and download operations. Review restored memberships, credential revocations, missing/newer immutable archives, object availability, access, original encryption-key custody and representative file restores before a recovery operator clears that marker. This is an offline operator decision; the web console does not silently approve recovery.

The initial synthetic local Postgres drill on November 20 restored 23 metadata tables and 166 synthetic file records. A later production metadata recovery and off-site SVB2 recovery also passed; see the dated update below. The source object store is separately required for actual file restoration.

## Remaining independent acceptance

Verify the production restricted runtime role, archive permissions/retention, scheduled-run success, recovery-key custody, encrypted off-host metadata backup and actual isolated production-metadata recovery. Test production MFA enrollment/recovery/revocation and representative practice files. The 50 GiB configured ceiling is not a tested throughput commitment. Endpoint encryption, source consistency, manufacturer-approved imaging exports, external monitoring and recovery ownership require separate operational acceptance. Contract/review gates are not bypassed by the security job.

# Managed recovery and production acceptance

## Deployed architecture

Hourly metadata backups run at minute 7 UTC through `/internal/metadata-backup`. The existing security job remains every 15 minutes. Both use `CRON_SECRET`; manual requests do not count as scheduled execution or send successful schedule heartbeats. A database lease excludes concurrent backup jobs. The production database owner is never required by either runtime job.

A separate `sv-recovery-*` private bucket holds only encrypted metadata bundles. Its lifecycle hides `metadata/` objects after 30 days and deletes hidden versions after another day; provider lifecycle processing is asynchronous, so physical deletion is not an exact 30-day deadline. The writer has read/write access to that bucket and no deletion or management permissions. Client file buckets and the 365-day locked audit bucket are unchanged. Recovery backups have no Object Lock.

New SVB2 bundles use an independent AES-256-GCM data key for each snapshot and RSA-OAEP-SHA256 wrapping with a 3072-bit recovery public key. Only the public key is stored in the portal. The private PEM key must remain outside Vercel, in the business password manager with MFA and documented emergency access. Do not paste it into a chat or place it in the recovery bucket. SVB1 bundles still require their original independent symmetric recovery key.

Each backup takes a repeatable-read snapshot, verifies existing credential decryption, enforces the 64 MiB plaintext limit, and warns at 48 MiB. Each uploaded bundle is downloaded again and checked for matching hash, size, manifest, and AES-256 storage encryption. Once daily a retained prior bundle is also read back. These cloud checks verify ciphertext integrity; only an isolated offline restore with the private key verifies decryption. No plaintext backup is uploaded.

Operational histories, notification queues, and readiness approvals are deliberately not restored from bundles; immutable log chains and the original 23 metadata tables are preserved. The recovery-review marker blocks normal file access, and restored device credentials are revoked. Backup jobs also refuse to run in a recovered environment pending review.

## Initial setup and repeatable restore

`tools/provision-metadata-recovery.mjs` requires the owner migration connection, stable credential-encryption key, existing restricted runtime connection (`RUNTIME_DATABASE_URL`), authenticated B2 CLI, verified production account fingerprint, HTTPS origin, and `--confirm-30-day-recovery`. It creates only the recovery bucket, scoped writer and recovery key pair, records encrypted writer credentials, applies migration 5, and grants the existing restricted role access to the three operational tables. It never enables Object Lock. Keys are written as protected local `.env.recovery-private.pem` and `.env.recovery-public.pem`; keep the private key outside Git and move custody to the password manager after verifying its stored copy. Existing setup is reused, not silently rekeyed.

Monthly restore procedure:

1. Select a verified backup from the dedicated recovery bucket. Download to a protected operator location and compare its recorded SHA-256 before decrypting.
2. Export the private PEM from the password manager to a temporary protected operator file. Never put it into the application runtime.
3. Create a new isolated, empty database. Set protected `RESTORE_DATABASE_URL`, the distinct source `DATABASE_URL`, and `RECOVERY_PRIVATE_KEY_FILE`.
4. Run `node --env-file=<protected-environment> tools/security-backup.mjs restore --file <downloaded.svbackup> --confirm-isolated-target --key-output <new-protected-key.env>`.
5. Verify complete audit/security log chains from the beginning; confirm workspace credential decryption, original file/bucket bindings, empty sessions/enrollments, all device credentials revoked, and the recovery-review marker. Download representative test files and compare them with their known source checksums.
6. Record duration, backup identifier, results, and exclusions in the acceptance evidence. Keep the isolated environment blocked and separate from production. Remove temporary private-key exports only after password-manager recovery was tested.

The automated backup target is no more than one hour of metadata loss during normal scheduling. A delayed or failed backup raises an operational alert; this is not a guarantee. The four-hour recovery target covers portal recovery, not downloading all imaging data. Independent operator and provider access are prerequisites.

## Acceptance checklist

Use MSP console > Security & logs > Record acceptance evidence only for completed checks. References must be short, non-sensitive ticket or evidence identifiers. Reviews expire after 30 days. Technical approval requires current checks plus an explicit activation review; provider review flags remain separate and are never changed by this feature.

- **Key custody:** export the private key from the actual business password manager and repeat decryption. Record emergency access ownership and an independent secured recovery copy.
- **MFA:** use a dedicated Clerk test identity, never the only administrator. Test enrollment, absent and stale second factors, account recovery, session revocation and removed-member denial. Preserve owner access.
- **Access:** verify viewer/uploader/editor/admin behavior and cross-practice list/upload/download/admin denial.
- **Notifications:** send a dashboard test, verify actual business inbox receipt, simulate a failed delivery and confirm visible retry/failure status, then verify incident recovery email.
- **Monitoring:** deliberately pause a disposable test check to verify missing-job email, and test failure and recovery signals. Confirm the actual scheduled jobs are sending separate signals. Test public availability workflow dispatch. Do not spoof production cron headers to claim scheduler evidence.
- **Credentials:** review previously exposed secrets and complete necessary rotation without changing the stable storage encryption key without a migration.
- **Endpoint:** confirm disk encryption, patched Windows, protected uploader folders and manufacturer-approved imaging export method. Live application database files are not assumed to be safe file-copy sources.
- **Pilot:** use Sorski's designated local non-patient folder; enroll its actual Windows computer with a one-time credential. New uploader defaults are every day at 21:00 using the computer's local time. The computer must be awake/online. Observe two successful scheduled nights, then test a changed file, interrupted/resumed transfer, restart, quota rejection, revoke/re-enroll, and checksum-verified downloads. Never delete source or client cloud files as part of the pilot.

New internal API: GET `/internal/metadata-backup` (cron-secret authentication). New MSP-only API: POST `/api/msp/security/backup`, `/test-notification`, `/evidence` under the same prefix. Existing MFA/origin/CSRF protections apply. Security status includes backups, notification attempts and readiness evidence without keys or bundle contents.
